1. PROJECT OVERVIEW
================================================================================

River Observatories for the Indo-Gangetic Plains is a public research portal
for river science. Visitors can browse 12 river observatories and explore
hydrology graphs, GIS maps, and interpreted data. Staff (Admin / Researcher)
have separate tools for data import, dataset management, user administration,
and audit logging.

Key principle: Public visitors see ONLY aggregate summaries and maps.
Detailed observation rows and CSV exports are restricted to authorized staff.

5. ROLE-BASED ACCESS CONTROL (RBAC) — DETAILED
================================================================================

5.1 THE THREE ROLES
--------------------------------------------------------------------------

Role         | Level | Description
-------------|-------|----------------------------------------------------------
VIEWER       |   0   | Default role for new accounts. Can sign in and see their
             |       | own profile. No staff tools. Same data access as public.
RESEARCHER   |   1   | Can upload data, create imports, validate data, submit
             |       | for approval. Can view own imports and submissions.
ADMIN        |   2   | Full access. Can manage users, rivers, geography, datasets,
             |       | approve/reject imports, view audit logs, export CSV.

5.2 ROLE HIERARCHY
--------------------------------------------------------------------------

Roles are HIERARCHICAL. A check for RESEARCHER also passes for ADMIN.

    ADMIN (2) > RESEARCHER (1) > VIEWER (0)

Code (auth.tsx, line 15):
    const ROLE_LEVEL: Record<Role, number> = { VIEWER: 0, RESEARCHER: 1, ADMIN: 2 };

    hasRole(required) => ROLE_LEVEL[user.role] >= ROLE_LEVEL[required]

5.3 WHERE RBAC IS ENFORCED
--------------------------------------------------------------------------

LAYER 1 — Frontend (Navigation Gate):
    • AdminLayout wraps /admin/* with <RequireRole role="ADMIN">
    • ResearcherLayout wraps /researcher/* with <RequireRole role="RESEARCHER">
    • RequireRole component checks useAuth().hasRole() and redirects to /login
      if the user doesn't have the required role.

LAYER 2 — Backend API (Edge Function — the REAL security boundary):
    • The "caller()" function extracts the Bearer token, verifies it via
      Supabase Auth, then loads the User profile from the database.
    • The "requireRole()" function throws 401/403 if the user is missing
      or doesn't have one of the specified roles.
    • Each API route explicitly calls requireRole() with the allowed roles.

LAYER 3 — Database (RLS + Grants):
    • Row Level Security (RLS) policies are defined in the migrations.
    • Browser roles do NOT have direct table grants.
    • All data access goes through the Edge Function using the service role key.
    • The "published_only" flag is passed to RPCs to filter data based on
      whether the caller is a public visitor or an authorized staff member.

6. DATA MODEL (DATABASE TABLES)
================================================================================

Core Tables:
    • River              — 12 river observatories (Ganga, Chambal, Gandak, etc.)
    • MonitoringStation   — Physical observation stations along rivers
    • RiverStretch        — Named river segments/stretches
    • State               — Indian states
    • District            — Districts within states
    • HydrologyParameter  — Measured parameters (water level, flow, etc.)
    • DataSource           — Origin of datasets (agency, project, etc.)

Data Tables:
    • Dataset             — Named datasets with status lifecycle
                            (DRAFT → SUBMITTED → APPROVED → PUBLISHED / REJECTED / ARCHIVED)
    • HydrologyRecord     — Individual observations (the actual measurement data)

Import/Workflow Tables:
    • Import              — Tracks data import jobs (file upload or Google Sheet fetch)
    • ImportStage          — Staging area for raw imported rows before validation
    • ImportError          — Validation errors per imported row
    • Submission           — Researcher submissions for admin review
                            (PENDING → APPROVED / REJECTED)

GIS Tables:
    • GisLayer            — Named GIS layers with visibility settings

User/Auth Tables:
    • User                — Application user profile (synced with Supabase Auth)
                            Fields: id, email, name, role, active, createdAt

Logging:
    • AuditLog            — Action audit trail
    • Report              — Saved visualizations/queries by staff

Key SQL RPC Functions:
    • wct_portal_rivers       — Public river listing with station/dataset counts
    • wct_portal_river        — Detailed single river view
    • wct_filter_options      — Available filter values for hydrology explorer
    • wct_hydrology_metrics   — Aggregate stats: summary, timeseries, annual, monthly, seasonal, heatmap
    • wct_hydrology_distribution — Histogram + percentile statistics
    • wct_hydrology_compare   — Compare data across stations, years, seasons, periods
    • wct_hydrology_extremes  — Highest/lowest observations (staff only)
    • wct_hydrology_scatter   — Scatter plot data (staff only)
    • wct_filtered_records    — Individual rows with pagination (staff only)
    • wct_geojson             — GeoJSON features for map rendering
    • wct_validate_import     — Validate staged import data
    • wct_commit_import       — Approve and commit import to production tables
    • wct_dataset_counts      — Per-dataset record counts
    • wct_admin_counts        — Admin dashboard aggregate stats

7. AUTHENTICATION FLOW
================================================================================

Step 1: User visits /login and enters email + password.

Step 2: Frontend calls supabase.auth.signInWithPassword({ email, password }).
         Supabase Auth returns an access token (JWT) + refresh token.

Step 3: Frontend calls GET /auth/me on the Edge Function with the JWT
         in the Authorization header.

Step 4: Edge Function:
         a. Extracts the Bearer token.
         b. Calls Supabase Auth API (GET /auth/v1/user) to verify the token.
         c. Loads the matching User profile from the "User" table.
         d. Checks that the user is active.
         e. Returns the user profile (id, email, name, role, active).

Step 5: Frontend stores the user in React context (AuthProvider).
         The useAuth() hook provides: user, loading, login, logout, hasRole.

Step 6: On sign-out, supabase.auth.signOut() clears the session.

Step 7: Auth state changes are monitored via onAuthStateChange listener.
         If SIGNED_OUT event fires, user state is cleared.

9. DATA FLOW
================================================================================

9.1 PUBLIC GRAPH VIEWING
--------------------------------------------------------------------------

    User opens /data or /rivers/:riverId
        → React component calls api.get('/hydrology/summary?riverId=...')
        → api.ts attaches the Supabase publishable key + optional JWT
        → Fetch hits Edge Function at /hydrology/summary
        → Edge Function calls RPC wct_hydrology_metrics with published_only=true
        → Postgres executes aggregate SQL (no individual rows exposed)
        → JSON summary returned → ECharts renders graph

9.2 MAP VIEWING
--------------------------------------------------------------------------

    User opens /gis
        → RiverMap component requests /gis/layers (public layers only)
        → Requests /gis/geojson/:kind for station/river geometry
        → MapLibre renders GeoJSON features on top of OSM/Esri tiles
        → Station markers are clickable with popup info

9.3 STAFF DATA IMPORT (Admin or Researcher)
--------------------------------------------------------------------------

    Step 1: Staff opens /admin/import or /researcher/upload
    Step 2: Selects import source:
            a) File upload (CSV or XLSX) — parsed client-side with ExcelJS
            b) Google Sheet URL — fetched server-side as CSV export
    Step 3: ImportWizard sends POST /imports with headers + row count
    Step 4: Client sends rows in batches via POST /imports/:id/rows
    Step 5: Client sends POST /imports/:id/validate with column mapping
            → Edge Function calls RPC wct_validate_import
            → Returns validation summary (valid/invalid/duplicate counts)
    Step 6: Researcher submits via POST /imports/:id/submit
            → Creates a Submission record (status: PENDING)
    Step 7: Admin reviews at /admin/datasets or via submission review
            → POST /submissions/:id/review with decision (APPROVED/REJECTED)
            → If approved: calls RPC wct_commit_import to move staged data
              into production HydrologyRecord table

9.4 DATASET LIFECYCLE
--------------------------------------------------------------------------

    DRAFT → SUBMITTED → APPROVED → PUBLISHED
                      ↘ REJECTED
    PUBLISHED → ARCHIVED

    Only PUBLISHED datasets and their records are visible to the public.

9.5 USER SIGN-IN
--------------------------------------------------------------------------

    Login form → Supabase Auth (signInWithPassword)
        → JWT token → GET /auth/me → User profile + role
        → React context updates → staff navigation appears

14. DEPLOYMENT
================================================================================

• Frontend: Built as static files → served by Nginx in Docker container.
• Backend: Edge Function deployed to Supabase (separate from frontend).
• Database: Hosted on Supabase Postgres.
• Auth: Supabase Auth service.

Docker Compose maps container port 80 → host port 3000.
Browser calls Supabase directly; the Docker container does NOT run the database
or Edge Function.

Migrations are applied to the Supabase database in filename order.
The Edge Function (portal-api/index.ts) is deployed via Supabase CLI or dashboard.


================================================================================
15. KEY DESIGN DECISIONS
================================================================================

1. PUBLIC = AGGREGATE ONLY: Public visitors never see individual observation
   rows or get CSV exports. Only summaries, charts, and maps.

2. SINGLE EDGE FUNCTION: The entire backend is one file (index.ts, ~400 lines).
   No separate Express server. All routing is done with path parsing.

3. SERVICE KEY PATTERN: The Edge Function uses the Supabase service role key
   for all database access. The browser only has the publishable key.
   This means RLS is bypassed server-side, and the Edge Function itself
   is the access control boundary.

4. FIXED RIVER LIST: The 12 observatories are hardcoded in observatories.ts.
   Database rivers must match these slugs to appear in the UI.

5. EMAIL-BASED DATA REQUESTS: Data access requests open a mailto: draft.
   There is no in-app request/approval workflow for external users.

6. IMPORT STAGING: All imports go through staging → validation → approval.
   Nothing reaches the production HydrologyRecord table without admin approval.

7. NO GLOBAL STATE LIBRARY: Auth context is the only global state.
   Everything else is local component state or URL query parameters.

================================================================================

• /gis/nearest returns an empty list — river geometry not supplied
• Several research categories have UI but need verified datasets
• Demo seed contains 20 SYNTHETIC water-level observations (not real data)
• Unsupported hydrology subroutes return HTTP 501
• Contact page opens email draft — no in-app request system
• PostGIS installed in "public" schema — review security finding
• No automated tests or lint scripts in package.json
• Build produces chunks >500 kB (ExcelJS is large)
